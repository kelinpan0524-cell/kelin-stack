# 分支看板

回答一个问题：**这个仓库现在每条线在哪、安不安全、我该做什么**。先给结论，按"要用户做什么"分组，对每条没进主干的分支给一句人话改动说明和一条建议。

## 核心规则

- **只读，只报不动**：推送、合并、删除分支、清理工作树全部等用户确认后由人或其他 skill 执行；
- **脚本采客观事实，判断交给模型**：脚本算位置/推送/合入状态；"改了什么、建议怎么办"由 agent 读提交说明后用人话写，不复述 git 术语；
- **读不到的不猜**：PR 信息拿不到就不写，注明"PR 信息不可用"。

## 跑看板

```sh
node "$SKILL_DIR"/scripts/branches.mjs --workspace "<项目路径>" [--fetch] [--json]
```

`--fetch` 会执行 `git fetch --prune`（更新并清理本地的远端跟踪引用），不改任何分支本身；没网络时去掉它并说明云端状态可能过期。`--json` 给机器消费。

## 合入状态五分类

| 状态 | 含义 | 处理 |
| --- | --- | --- |
| `merged` | 是主干祖先（普通合并） | 可清理候选 |
| `squash_merged` | 分支改动已整体进主干（树内容一致） | 可清理候选 |
| `rebase_merged` | 每个提交都在主干有等价补丁 | 可清理候选 |
| `no_own_commits` | 相对主干没有独立提交（刚建或已快进） | **先问用户**，脚本分不清 |
| `unmerged` | 没进主干 | 看分组和 flags |

只有前三种**且无未提交改动**才算可清理；`no_own_commits` 永远先问。squash 判定是启发式（比对树内容一致），标记后建议人工再核一眼。

## 分组与措辞

- **需要你决定**：`local_only`（只在这台电脑，删了找不回）、`remote_deleted_unmerged`（云端删了但没进主干）、`closed_pr_unmerged`（PR 关了没进主干）、unmerged 且无近期活动的；
- **正在进行**：unmerged 且有未提交改动或 14 天内有活动；
- **已进主干，可以清理**：只列数量和前几个名字，等用户说"清理"再给全清单。

每条分支读它的提交说明，用一句用户听得懂的话写"改了什么"，再给一条建议和理由（可选：开 PR 合进主干 / 继续做 / 先推云端保存 / 放弃并删除 / 先确认是谁在做）。

## 主干健康

看板顶部先说主干：本机与云端是否一致、本机有没有没走 PR 的提交、主工作区脏不脏。本机主干领先云端（绕过了 PR）要标警示。

## 下游衔接

| 下一步 | 去哪 |
| --- | --- |
| 用户确认合并某条分支 | `kelin-ship` 走纪律合并（review 回执 CURRENT 才合） |
| 用户确认清理 | 逐条列清单确认后 `git worktree remove` / 删分支，一次一类 |
| 看板暴露的问题要复盘 | `kelin-reflect`；"总是绕过 PR"类习惯写进 AGENTS.md |
| 要看项目整体进度 | `kelin-recall`（分支只是它的一个输入） |
