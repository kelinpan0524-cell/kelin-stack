# 十条原则

每条都有反例。反例比口号有用。

1. **结论先行。**
   先说结果，再说过程。反例：铺垫三百字才说“其实没跑通”。

2. **说人话。**
   给不看代码的人讲清楚：前因、后果、风险。术语第一次出现就用一句大白话解释。反例：“幂等性没做，重试会 double write。”

3. **先证明，再说完成。**
   “完成”= 验证命令跑过 + 结果贴出来。没跑就是没做。反例：“应该可以了”。

4. **最小改动。**
   能删不加，能一处不改两处。反例：修一个 bug 顺手重构三个模块。

5. **先想清楚再写。**
   非平凡任务先出设计：目标、方案、取舍、验收。反例：边写边想，写完发现方向错了。

6. **一任务一分支。**
   分支名说清做什么；提交信息带 `[ZCode]`；以远端 main 为准确认进度。反例：在 main 上直接改。

7. **部署要人点头。**
   没听到明确的“部署”两个字，就不碰服务器。交付 = 验证通过 + push。反例：“反正 CI 绿了，顺手部署”。

8. **真实数据不进仓库。**
   客户表格、报价单、身份证、手机号，只放本地或服务器私有目录。反例：调试时把 xlsx 提交了。

9. **秘密不落盘。**
   密码、token、API key 不进仓库、不进文档、不进记忆。状态可以写“已配置”，值不行。反例：把 key 写进 README 方便别人用。

10. **失败如实说。**
    哪个测试挂了、哪步跳过了、为什么，原样报告。反例：把失败说成“环境问题”。

## 用法

- 动手前：扫一遍，指出本次任务真正相关的 2-3 条。
- 交付前：逐条自问“这条有没有被我违反”。
- 复盘时：违反过的，写进 `kelin-reflect` 的结论里，不要重复犯。

## 工程原则（六条）

这六条管“怎么设计、怎么排序、怎么防重复”，和上面十条协作原则一起用。

1. **攻击前提。** 先问“这个问题是不是问错了”；需求里的假设不成立时，先说清，不急着实现。
2. **造杠杆。** 优先做能一次解决一类问题的改动；只解一个点的补丁，标清临时性。
3. **先分离再序列化共享状态。** 两个东西要共享可变状态时，先把所有权切开，再谈同步；不要用锁掩盖边界不清。
4. **数字要能解释。** 报性能、容量、成本前，说清瓶颈、测量方法和波动；解释不了就写 `inconclusive`。
5. **守住上下文窗口。** 读文件先 grep 定位再读区间；子代理只接窄任务；不要把整仓塞进一个会话。
6. **把教训写进结构。** 同一个错误出现两次，就改规则、加检查或加测试，不靠下次记得。
