# 多仓库统筹

仓库一多，乱的不是代码，是**谁拥有什么数据、谁依赖谁、改一个要发几个仓**。先画图，再动手。

## 先画地图

维护一份 `repo-map.json`：

```json
{
  "repos": [
    {
      "name": "quote-api",
      "path": "../quote-api",
      "owner": "报价组",
      "purpose": "报价计算与存储",
      "deploy": "独立发布",
      "dependsOn": ["auth-api"],
      "contracts": ["openapi.yaml"],
      "ownsData": ["quotes", "quote_lines"]
    }
  ]
}
```

字段含义：

- `owner`：唯一负责团队，出问题找谁；
- `dependsOn`：运行时依赖，不是代码引用；
- `contracts`：对外契约文件（OpenAPI/Proto/JSON Schema）；
- `ownsData`：这个仓库是哪些数据实体的**唯一写入者**。

校验：

```sh
node skills/kelin-multirepo/scripts/repo-check.mjs repo-map.json
```

它检查：名字唯一、必填字段齐全、依赖存在、没有循环依赖、契约文件存在、同一个数据实体没有两个 owner。

## 选集成方式

| 场景 | 推荐 | 不要 |
| --- | --- | --- |
| 同一个可部署单元、强事务 | 同库或 monorepo | 拆成多个服务还共享事务 |
| 独立部署、独立团队 | API 或事件 | 直连对方数据库 |
| 遗留共享库 | 指定单一所有者，其他只读视图 | 两个仓库都写同一张表 |
| 跨仓共享代码 | 版本化包或契约生成 | 复制 DTO、复制模型 |
| 报表/分析 | 只读副本或数仓 | 在主库上跑大查询 |

**共享库表是最贵的耦合**：一个字段改动要协调所有仓库发布，还容易出现两边写入不一致。能走 API/事件就不要共库。

## 契约优先

- 契约先行：OpenAPI / Protobuf / JSON Schema，先定再实现；
- 只做加法：加字段、加可选参数；重命名和删除要分版本；
- 权威声明：provider 的契约是真相，consumer 以它为准；
- 消费者契约测试：provider 改动能提前发现谁会挂；
- 版本窗口：旧版本保留多久、什么时候下线，写进契约；
- 契约文件放一个共用位置或用 submodule，不要每个仓手抄一份。

## 跨仓改动顺序

1. 改契约，保持向后兼容；
2. provider 先发布新版本；
3. consumer 逐个升级，观察错误率；
4. 确认没有旧调用后，再删旧字段/旧接口；
5. 每一步都能单独回滚。

不要“三个仓库同时发”，也不要先改 consumer 再改 provider。

## 老项目多仓改造

1. 冻结新增的跨库写入：新功能只能走 API/事件；
2. 找最痛的一条业务链路做纵向切片，不要横向重构所有仓；
3. 用契约测试和特征测试锁住现状；
4. 每切一刀，写清部署顺序和回滚方式；
5. 数据迁移单独排期，不和功能改动混在一起。

## 和别的 skill 的关系

- `kelin-map`：单仓内部的功能地图；这里是仓库之间的地图；
- `kelin-legacy`：单仓改造方法；多仓先做本 skill 的地图；
- `kelin-blast-radius`：改一个仓时，用它算跨仓影响面；
- `kelin-audit`：多仓审计先看 `repo-check` 的冲突。

## 反模式

- 两个仓库同时写一张表；
- 每个仓复制一份 DTO，字段各改各的；
- 没有部署顺序，谁先发谁倒霉；
- 跨仓改动只在一个仓跑测试；
- 为了“统一”把无关仓库硬塞进 monorepo。
