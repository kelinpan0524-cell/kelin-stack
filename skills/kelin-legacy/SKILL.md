# 老仓库改造

老仓库最大的风险不是代码丑，是**你不知道改坏了什么**。所以顺序永远是：先能验证，再改。

## 第 0 步：基线

在动任何代码之前，记录：

```sh
# 能不能装、能不能构建、能不能测
<install>
<build>
<test>
```

输出一张基线表：

| 项 | 状态 | 证据 |
| --- | --- | --- |
| 依赖安装 | 成功/失败 | 命令 + 输出 |
| 构建 | 成功/失败 | 命令 + 输出 |
| 测试 | 通过 N / 失败 M / 跳过 K | 输出 |
| 启动 | 能/不能 | 端口、日志 |

**本来就失败的测试单独列出来**，不要混进后续结论。

## 第 1 步：地图与热点

- 用 `kelin-map` 建功能地图（路径 → 功能 → 怎么验证）；
- 找热点：改动最频繁 × 最复杂的文件。

```sh
git log --since="12 months ago" --name-only --pretty=format: | sort | uniq -c | sort -rn | head -20
```

热点就是最值得先补测试的地方。

## 第 2 步：特征测试（characterization tests）

给要改的模块补“锁住现状”的测试：**断言它现在实际做什么，而不是应该做什么**。

- 输入从真实调用方取；
- 输出存成 golden 文件或断言；
- 现有 bug 也锁住，并在测试里注明“这是现状，不是正确行为”。

有了这层，后面的重构才有安全网。

## 第 3 步：切片改造

一次只动一个缝：

1. 选一个边界清楚的部分（一个模块、一个接口、一张表）；
2. 在旧实现外面加一层适配，新实现从后面接进来；
3. 新旧并行跑，差分对照（见 `kelin-correctness`）；
4. 确认一致后切流量/切调用，旧实现保留一个版本再删；
5. 每一片都能独立回滚。

**禁止**：大爆炸重写、和重构同一个 PR 里升级依赖、一次改多个缝。

## 第 4 步：每片的验收

```sh
node skills/kelin-verify/scripts/run-acceptance.mjs verify.json
```

验收至少包含：特征测试全过、新测试全过、差分对照一致、启动正常。

## 优先级

按“出错代价 × 发生概率”排序，不按代码新旧：

1. 会丢数据、泄密、算错钱的；
2. 主流程经常挂的；
3. 挡住后续开发的（比如没有测试、构建要 40 分钟）；
4. 只是难看的。

## 输出

```markdown
## 基线
## 地图与热点（前 5）
## 特征测试覆盖了哪些现状
## 切片计划
- 切片 1：范围 / 验证 / 回滚
## 已完成的切片与证据
```

## 反模式

- 先重构再补测试；
- 一边重构一边加新功能；
- 拿“代码覆盖率”当安全网，却没断言行为；
- 一次改十个文件，出事不知道回滚哪。
