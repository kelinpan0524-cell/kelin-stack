# 界面审查

先看渲染结果，再谈审美。**没有截图或实际页面，不下结论。**

## 和 impeccable 的关系

如果环境里有 `impeccable` skill，直接用它（在 ZCode 里写 `/skill impeccable critique <target>`）：

- 深度 UX 评审：impeccable 的 `critique` 流程
- 技术质量审查（a11y、性能、响应式）：impeccable 的 `audit` 流程
- 精修收尾：impeccable 的 `polish` 流程

没有 impeccable，就按下面的清单自己走，结论一样要给证据。

## 先确认四件事

1. **这是什么界面**：营销页（说服）、工具（完成任务）、文档（读懂）、作品集（展示）。不同目标，标准不同；
2. **在什么尺寸用**：手机、平板、桌面，最小和最大宽度各是多少；
3. **数据是什么状态**：空、加载中、出错、无权限、超长文本、大量数据；
4. **谁在用**：内部工具可以密，面向客户要克制。

## 审查维度

**层级与布局**
- 第一眼看到的是不是最重要的东西；
- 对齐、间距、分组是否有一致的节奏；
- 信息密度是否匹配场景（工具可以密，营销页要留白）。

**状态完整性**
- 空状态：有没有引导，而不是一片空白；
- 加载：有没有骨架或进度，避免布局跳动；
- 错误：说清发生了什么、怎么恢复；
- 禁用/无权限：是否解释了原因；
- 超长/超多：截断、换行、滚动是否正常。

**响应式**
- 最小宽度下是否横向滚动；
- 触控目标是否 ≥44px；
- 文字是否被挤压或重叠；
- 表格/图表在窄屏是否可用。

**可访问性**
- 对比度是否达标（正文 4.5:1，大字 3:1）；
- 键盘能否走完全部操作，焦点是否可见；
- 图片有没有 alt，表单有没有 label；
- 语义标签和标题层级是否正确；
- 动效是否尊重 `prefers-reduced-motion`。

**文案**
- 按钮说动词，不说“确定”；
- 错误信息说“怎么修”，不只说“失败了”；
- 术语一致，中英文不混用。

**性能**
- 图片尺寸是否按实际显示裁剪，有没有用原图缩；
- 字体是否造成闪烁或布局抖动；
- 首屏是否被大组件或阻塞脚本拖慢。

## 输出

```markdown
## 结论
P0: 0 / P1: 2 / P2: 4 / P3: 3 —— 建议先修 P1

## P1
1. **移动端表格横向溢出**（`src/QuoteTable.tsx:88`）
   - 场景：iPhone 13，1280 行数据
   - 现象：表格宽 980px，页面出现横向滚动，操作列看不到
   - 改法：窄屏改成卡片列表，或固定操作列 + 横向滚动容器
   - 验证：375px 截图 + 无横向滚动

## 已检查且没问题
- 对比度：正文 7.2:1
- 键盘：表单可完整操作
```

每条都要有：页面/组件位置、触发条件、看到的现象、改法、怎么复验。

## 和 audit / verify 的衔接

- `kelin-audit` 遇到前端仓库，把本 skill 的六个维度作为“界面”一类并入报告；
- `kelin-verify` 的验收清单里，UI 改动至少包含：一个目标尺寸截图、一个空状态、一个错误状态。

## 资源注意

- 用现有的 dev server，不重复起服务；
- 一次只开一个浏览器实例、一个视口，截完关掉；
- 不要为了审查同时跑构建和浏览器自动化；
- 大页面只截关键区域，不整页滚动几十屏。

## 反模式

- 只读代码就说“视觉没问题”；
- 只截桌面宽度；
- 把个人审美当问题，不给场景；
- 报“颜色不好看”但说不出对比度和目标用户。
