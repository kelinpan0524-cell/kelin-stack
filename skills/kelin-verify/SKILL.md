# 验证

“完成”不是一句判断，是一组能重复执行的断言。

## 核心规则

1. **先写验收，再动手。** 验收标准必须能落到命令、文件、接口响应或页面操作上。
2. **模型说“通过了”不算证据。** 只有命令退出码、输出内容、文件哈希、接口返回、截图算。
3. **先跑基线。** 改之前跑一遍，知道原本是什么状态；否则分不清是你改坏的还是本来坏的。
4. **失败如实报。** 挂了哪个、报什么错、哪步跳过，原样贴。

## 步骤

### 1. 写验收清单

每条一行，形如：

```
[ ] `npm test` 退出码 0
[ ] `curl /api/health` 返回 {"ok":true}
[ ] 生成的文件包含字段 `quote_id` 且行数 = 输入行数
[ ] 页面在 1280x800 下无横向滚动（截图）
```

写不出来的，说明这条需求还没定义清楚。

### 2. 跑基线

在改动前执行一遍，记录：哪些本来就通过、哪些本来就失败。本来就失败的，单独列出，不要混进本次结论。

### 3. 实现后逐条执行

- 命令类：记录完整命令、退出码、关键输出；
- 文件类：记录路径、大小、哈希、关键字段；
- 接口类：记录请求、状态码、响应体关键字段；
- 页面类：记录尺寸、截图路径。

### 4. 交证据表

```markdown
| 断言 | 命令/操作 | 结果 | 证据 |
| --- | --- | --- | --- |
| 单测全过 | `npm test` | 通过 42/42 | 输出见下 |
```

## 界面改动

UI 改动不能只跑命令。用 `kelin-ui` 的清单，至少留三样证据：一个目标尺寸的截图、一个空状态、一个错误状态。装了 `impeccable` 的话，把它的 `critique` 和 `audit` 结论并进验收表。

## 插件/仓库级验证

如果被验证对象是一个 ZCode 插件（有 `skills/`、`agents/`、插件清单），用 `kelin-verify-stack` skill：它会体检环境、按改动路径算出该测什么、真的开无头会话调用 skill，并输出带哈希的回执。

## 反模式

- 只跑 happy path；
- 用“应该”“理论上”代替执行；
- 测试失败后改测试让它过；
- 把跳过说成通过。

## 配套脚本

把验收清单写成 `verify.json`，一次跑完并留下证据：

```json
{ "checks": [
  { "id": "unit", "cmd": "npm test" },
  { "id": "health", "cmd": "curl -fsS localhost:3000/health" }
] }
```

```sh
node skills/kelin-verify/scripts/run-acceptance.mjs verify.json
```

逐条打印 PASS/FAIL 和耗时，最后输出 JSON 汇总；任何一条失败，退出码为 1。
