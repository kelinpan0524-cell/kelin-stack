# 拷问

不是审阅，也不是给方案。是用一轮一轮的问题，把一个还没想透的东西逼到没有悬空假设。

审阅的问题是：**给了方案就等于替他想了**——他立刻从“思考”切换成“评价你的方案”，自己的漏洞一个没动。

来源：Matt Pocock 的 grilling（`mattpocock/skills`，MIT，2026-11-18 版）。原版只有一段话，这版补了分工、反模式和衔接。

## 设计树 + 轮次

把话题画成一棵**设计树**：每个决定往下分叉成依赖它的决定。

- **前沿（frontier）**：所有前置条件已经定下、现在就能问的决策。
- 一轮问完整个前沿：每题编号，每题**给出推荐答案**。
- 措辞要让对方回一个“是”就能接受推荐。
- 他答完，前沿外扩，重新算，再问下一轮。
- 某个问题依赖同一轮里还没答的另一题，它属于**下一轮**，不属于这一轮。

一轮的格式：

```
❓ **Q1** — **<问题标题>**：<正文，可多段，可带选项>

➡️ <我的推荐>

---

❓ **Q2** — **<问题标题>**：…
```

## 三条硬规则

1. **找事实的是我，不是他。** 需要文件、命令行、接口返回的事实，自己去查（必要时派子代理带干净上下文去查）。不要拿“你们接口长什么样”去问他。
2. **做决定的是他。** 每个决策摆到面前、给推荐，然后等。推荐不等于替他拍板。
3. **不静默假设。** 分叉没走完不算想清楚；没说出口的默认值，就是没定的决策。

## 什么时候算收

前沿空了：设计树每个分叉都走过，没有任何东西被默默假设。**在他确认达成共识之前，不动手实现。**

## 和别的 skill 怎么分工

| 场景 | 用谁 |
| --- | --- |
| 先把问题问干净，再谈怎么做 | 本 skill，在 `kelin-plan` 前面 |
| 需求没说清、环境没摸清 | `kelin-product`；grill 比它狠——不帮你想，只逼你想 |
| 想清楚了要落成可判定的契约 | `kelin-goal` |
| 跨模块要出设计草图，草图里有开放决策 | `kelin-architect` 出图，再用本 skill 逐个问掉 |
| 已经成形、只要挑毛病 | `kelin-review`，不是本 skill |

## 反模式

- 一次抛十个问题不分轮次，对方直接弃疗；
- 给了推荐就自己往下做，没等回答；
- 把能查的事实做成问题问人；
- 最后一行说“我理解了”，其实中间跳过了分叉；
- 用“你觉得呢”结尾——问题要具体到一个能定的决定。
