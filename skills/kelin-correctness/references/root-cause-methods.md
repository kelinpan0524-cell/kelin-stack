# 根因排查方法

原因不明的缺陷，按手头有什么线索选方法，可以组合。每做一次实验，先想好"如果是它，就会看到什么"，一次只改一个变量。

## 1. 以前是好的：缩小到具体提交

先看中间隔了多少提交：

```sh
git log --oneline <好的>..<坏的>
```

提交不多或能猜到范围，直接读相关改动：`git log --oneline <好的>..<坏的> -- <文件>` 再 `git diff`。

提交多、看不出范围，用二分。**在临时 worktree 里跑**，不动当前工作区：

```sh
git worktree add --detach /tmp/bisect-wt <坏的>
cd /tmp/bisect-wt
git bisect start <坏的> <好的>
git bisect run <复现命令>
git bisect reset
cd <原仓库> && git worktree remove --force /tmp/bisect-wt
```

- 复现测试通常没提交，旧版本里没有它：开始前把它复制进临时目录，用新文件名避免冲突；
- `bisect run` 按退出码判断：0=正常，125=这个版本没法测、跳过（构建失败应返回 125）；
- 找到提交后读它的完整改动确认因果链，不只凭提交说明下结论；汇报里写短哈希和说明。

## 2. 有一个错误的值：往回追

从用户看到的错误输出出发，找到产生它的函数；沿调用链往上，在每个模块边界加一行临时日志打印这个值；找到"上一步还是对的、这一步变错了"的位置——缺陷在这一步，不在报错的地方。结束删掉全部临时日志。

## 3. 有能正常工作的对照：换差异

同时跑正常情况和出错情况（另一个输入、平台、配置），把差异逐项换成一致的，直到现象消失；最后换掉的那项就是触发条件。输入很大时逐步删减，找到最小触发输入。

## 4. 偶发问题：先固定不确定性

| 不确定性来源 | 固定办法 |
| --- | --- |
| 时区、当前时间 | 测试里指定时区或注入固定时间 |
| 随机数 | 固定种子 |
| 并发与时序 | 串行执行或加确定等待点 |
| 测试间共享状态 | 单独跑出错用例，再换顺序组合 |
| 外部服务、网络 | 本地替身或固定样本数据 |

找到来源后修掉不确定性本身；不用重试、sleep、加大超时掩盖。

## 5. 普遍问题的全仓排查

**按根因的写法搜索，不按报错信息搜索。** 例如根因是"时间戳转日期没指定时区"，就搜所有时间戳转日期的调用，逐个确认有没有指定时区。排查结果列清单：位置、是否同样有问题、怎么处理的。

## 算不算找到根因（两条全满足）

1. 能讲出从触发条件到现象的完整因果链，每一步对得上 `文件:行号`；
2. 能解释所有观察到的现象，包括为什么以前没出现、为什么只在某些情况出现。

## 这些不算修复

说不清坏值从哪来就在报错处加空值判断、try/catch、重试、sleep；只对报告的那个输入写特判；放宽或跳过失败的测试；一次改好几处说不清哪处起作用。
