# 设计草图

目标是**在便宜的时候发现方向错了**。草图不是流程图，是能被实现约束住的东西。

## 草图里必须有什么

1. **类型与签名**：核心数据结构、函数入口、返回值。用目标语言写，不用伪代码糊弄；
2. **模块边界**：谁拥有什么数据，谁调用谁，跨边界只传什么；
3. **数据流**：一次请求/一次任务从进入到结果，经过哪几步，每步失败会怎样；
4. **失败模式**：超时、重复、部分成功、并发，各自的处理策略；
5. **不做的事**：这次明确不解决的，写出来防止范围蔓延。

## 步骤

1. 用 5 行说清现状和约束；
2. 写 2 个方案，每个给：接口长什么样、改动面多大、失败怎么处理；
3. 明确推荐一个，并说为什么不选另一个；
4. 停在草图，等确认。除非用户已明确授权直接做。

## 输出

`design.md`，包含上面五块 + 一段“如果需求变了，哪里最先崩”。

## 反模式

- 只画框图，没有类型和签名；
- 方案只给一个，没有取舍；
- 草图里开始写实现细节；
- 不写“不做的事”，导致范围越做越大。
