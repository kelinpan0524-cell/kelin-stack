# 自审

> 命令里的 `$SKILL_DIR` 指本 Skill 所在目录的绝对路径，执行前先替换成实际路径。

审查的目标是**在用户发现之前发现问题**，不是证明自己写得好。

## 只报能证明的

每条问题必须带：

- 位置：`文件:行号`；
- 触发条件：什么输入/状态会出问题；
- 后果：会错成什么样；
- 建议：怎么改（一句话）。

“感觉不太对”“可能有问题”不报。

## 门禁完整性

门禁是任何能让这次改动失败的检查：测试、断言、阈值、超时、lint、类型检查、CI job、快照。审查时先扫门禁改动，再谈其他。

```sh
node "$SKILL_DIR"/scripts/gate-scan.mjs --base origin/main
```

脚本分三层，不能跳级：

1. **列出**：测试、CI、快照、配置里的每个 hunk，只计数，不算问题；
2. **阅读**：带标签的 hunk（删测试、关测试、快照独改、占位符、环境嗅探、抑制注解、绕过开关、放宽阈值、吞异常），逐个读；
3. **判定**：只问一个问题——**这次放宽是为了掩盖它原本要抓的失败，还是有本 diff 里看得见的测量或决策依据？**

门禁类发现一律**只问人，不自动修**。报告里写清标签、位置、前后值和那句问题；没有依据的放宽按 P1 起。

## 对抗审查

需要更狠地找 bug 时加 `--adversarial`：

- **硬约束：审查者必须跑在对面模型的 CLI 上**——Claude 系代理显式走 `kelin-delegate --runner codex --role review`（codex exec 只读沙箱）；Codex 系代理显式走 `claude -p --permission-mode plan`（本机 claude 版本不支持该模式或无法保证只读时，按"审查失败显性化"处理，不得以禁部分工具充当只读），均不经 delegate 路由；通用 delegate 角色路由只能作为对抗审查之外的补充视角，不能充当必需审查者。指定入口不可用时按"审查失败显性化"处理，禁止用运行在自家模型上的子代理或内部委托机制充当独立审查者，也不把本家模型的输出计为独立审查——那失去交叉意义。
- 只接受跑得出证据的发现：失败测试、复现脚本、命令输出；
- 风格、命名、未来风险、个人偏好一律丢弃；
- 每条发现交给 `kelin-verifier` 重跑确认；通用 delegate 角色路由（codex/agy 只读沙箱）只能作为对抗审查之外的补充视角，不能充当必需审查者，返回结果同样走回读剔除；
- 只报告，不修；修不修由人决定。

## 审查失败显性化

审查者的输出缺失、为空、超时或异常退出 = **显性失败**，不是"无发现"：结论里必须点名哪个审查者、何种失败，禁止静默当作"无发现"。委托命令必须带超时，且超时要有可诊断的退出码或标记，不得把超时读成"审查通过"。

本档全部必需审查者成功返回合法裁决（`CLEAN` / `FINDINGS`）且主裁完成裁决，才允许签评审回执；存在未消解的审查失败时，禁止签 `CURRENT`、禁止进自动合并——即使 P0/P1 计数为 0。

**结构化裁决与正文松绑**：`review-check --write` 与 `kelin-mode advance` 共用同一判定函数（`evaluateReviewReport`），支持两种写法：
- **推荐（结构化封面）**：报告顶部用 YAML frontmatter 声明 `verdict: clean | findings | failed`（可选 `reviewers:` 记录各审查者状态，任一非 `ok`/`pass`/`clean`/`findings` 即拒签），正文只需非空且无未闭环 P0/P1，正文中英文、代码块引用失败示例均不误伤；
- **兼容（末尾裁决行）**：无封面时，仅检查报告最末尾有效行是否为 `CLEAN` 或 `FINDINGS`（跳过 HTML 注释，不再满篇扫描），且仅对非代码块正文拦截行首"审查失败 / Review Failure"声明（不区分大小写）。

## Lead Judgment（主裁判断）

主代理按固定顺序处理外来发现：先去重 → 对每条去重后的发现回读取证并**怀疑式分诊**，明判 **修复 / 驳回（附代码证据）/ 交人拍板**（禁止逢评必改，也禁止把未经判断的发现清单原样转交派单）→ 筛出行动项；并点名三类典型噪音：误报、过度引申、把风格当实质。

**防钻牛角尖三条底线（吸收 pstack / open-pstack）**：
1. **可达 ≠ 有后果（实际使用面原则）**：只有系统真实调用链路会触发、且会改变真实结果的缺陷才算阻断项（P0/P1）；靠手工篡改状态、构造系统上游永不产出的怪异输入，或改完对真实结果无影响的防御性加固与偏好，归 P2/P3 或驳回，不拦交付。
2. **发现 ≠ 判决**：审查者可报告其看到的边界，但是否阻断交付由主裁对照实际使用面与意图拍板；未运行证实的推测只标"待确认"，不升格为必改项。
3. **拆前提止损**：同一前提连续 2 轮修不过同一个门禁，立刻停下质疑前提本身、改换结构方案，禁止继续叠第 3 层补丁。

"意图先行"只定审查视角，不豁免门禁完整性（gate-scan）与安全检查。

## 意图先行

审查开始先一句话写明**这次改动想达成什么**（从任务书或 PR 描述提炼）；所有审查只挑战"是否达成该意图"，不挑战意图本身；意图与发现一起出现在结论里。

## 子代理发现的回读剔除

独立审查（`kelin-reviewer` 子代理或外部模型）返回的每条问题，主代理都要**回读对应代码确认成立**才放进结论或交给执行者：读得出位置、对得上触发条件、讲得出后果的才算数；读不出依据的标"待确认"或记录驳回理由后剔除，不把未经核实的问题转手。防的是审查者的幻觉经你之手变成别人的返工单。

**委托审查的提示词必须写死输出契约**：逐条问题以 `文件路径:行号` 开头，跟触发条件、后果、建议；缺位置的条目一律按"待确认"处理，不计入已确认问题数（2026-11-17 fixture eval 实测：codex 侧委托审查没带 file:line，此条即为此而设）。

## 评审指纹

评审必须绑定当时的工作区。审完写回执：

```sh
node "$SKILL_DIR"/scripts/review-check.mjs --write
```

交付前再跑一次：

```sh
node "$SKILL_DIR"/scripts/review-check.mjs
```

`CURRENT` 才算评审有效；`STALE` 说明代码变了，评审作废；`UNVERIFIED` 或 `MISSING` 不能当通过。`kelin-ship` 只接受 `CURRENT`。

## 审查档位（按风险选深度，不一刀切）

| 档 | 适用改动 | 做什么 |
| --- | --- | --- |
| 轻量核验 | 纯样式/文案/排版、辅助脚本（且未碰高风险区） | gate-scan 看改动块，对照复用与文案配对快速核查，给简短结论 |
| 独立深审 | 核心逻辑，或动了并发/数据格式/迁移/删除类不可逆/鉴权支付/对外接口/发布链路 | gate-scan 采集 + 干净上下文五维细审（本 skill 全流程） |

高风险区的定义以目标仓库 AGENTS.md 开发约定为准；没有时按左列类别判断。轻量档允许快速核验、不强制全流程，但不省 gate-scan——门禁改动任何档位都要过。

体量维度与上表风险档位叠加，两者取更严者；体量档位绑定首轮审查范围，后续轮次按增量复验：

| 体量 | 审查深度 |
| --- | --- |
| < 50 行且 ≤ 2 个文件 | 轻量核验 |
| ≥ 50 行或 ≥ 3 个文件 | 独立深审 |
| > 200 行或 ≥ 5 个文件 | 独立深审 + 全量对抗审查（多视角） |

同时命中多档时按最高档执行；首轮覆盖完整 diff，深度按档位。

## 分级

| 级别 | 含义 | 例子 |
| --- | --- | --- |
| P0 | 会丢数据、泄密、把线上搞挂 | 没校验就覆盖用户数据；密钥写进仓库 |
| P1 | 主流程错误，用户能撞上 | 边界条件算错；异常被吞掉 |
| P2 | 局部错误或明显的坑 | 空数组没处理；错误信息误导 |
| P3 | 可读性、命名、重复代码 | 复制粘贴的三段逻辑 |

P0/P1 须有可达触发条件、实际后果和可核验证据；纯假设极端边界、风格偏好与无关存量归 P2/P3，记清单但不拦交付。P0/P1 必须修完；P2 记录或交人拍板；P3 留到下次。

## 检查清单

**正确性**
- 主要输入、边界值（空、0、负数、超长、并发）分别会怎样；
- 错误路径有没有被吞掉；
- 时间、时区、编码、小数精度。

**测试**
- 新增行为有没有测试；
- 测试是不是只测了实现细节，没测行为；
- 失败时能不能定位。

**安全与合规**
- 代码/配置/日志里有没有密钥、token、真实客户数据；
- SQL/命令拼接有没有注入风险；
- 权限是不是最小。

**范围**
- 有没有顺手改了不相关的东西；
- 有没有为了绕过一个报错而加的分支/开关/兼容层；
- 删除的代码是不是真的没人用。

## 输出格式

```markdown
---
verdict: findings
---

## 审查结论
P0: 0 / P1: 1 / P2: 3 / P3: 2 —— 建议：修完 P1 再交付

## P1
1. `src/quote.ts:88` 数量为 0 时除以 0，返回 Infinity，前端显示 ¥∞。
   触发：用户把数量清空再提交。
   建议：数量 <= 0 时直接拒绝并提示。

## 已检查且没问题
- 权限：接口复用了现有鉴权中间件（`src/auth.ts:12`）
```

最后一段“已检查且没问题”很重要：它告诉用户你审了哪些面，而不是只挑刺。`review-check --write` 优先读顶部 `verdict: clean | findings | failed`（正文自由书写、不误伤），也兼容无封面报告在最后一行写 `CLEAN` 或 `FINDINGS`。

## 反模式

- 把风格偏好当 P0；
- 只报问题不给建议；
- 报了一堆，没排序，用户不知道先修哪个。

## 审查与复验

- **首轮审范围**：全量走本 skill 与 `gate-scan.mjs`，审交付 diff 与直接调用链，一次列清问题；放行与签 CURRENT 的前提：全部必需审查者成功返回合法末行裁决且主裁完成裁决——无真实 P0/P1 且前提满足才立即放行。
- **复审只看增量**：第 2 轮起只核对上轮未关闭项、修复 diff 及直接回归，不重扫全仓挖新坑（偶遇影响本次交付的已确认严重问题除外）。
- **常态 2 轮，收敛可定点续验**：二审显示明确收敛（原阻塞已实质关闭，仅剩单点可定位、能复验的尾项或补丁回归）时，可继续定点复验，最多共 4 轮（含首轮，同版重跑或换会话沿用轮次）。
- **止损升级**：二审后未收敛、同一根因连续 2 次修复无进展、反复修 A 坏 B、需扩大范围/改方案/放宽门禁，或满 4 轮仍有阻塞，立刻停下用大白话带证据汇报由人拍板。
- **档位与轮次互不替代**：体量档位决定单轮审查深度，轮次上限约束修复后的复核轮数。
