# 自审

> 命令里的 `$SKILL_DIR` 指本 Skill 所在目录的绝对路径，执行前先替换成实际路径。

审查的目标是**在用户发现之前发现问题**，不是证明自己写得好。

## 只报能证明的

每条问题必须带：

- 位置：`文件:行号`；
- 触发条件：什么输入/状态会出问题；
- 后果：会错成什么样；
- 建议：怎么改（一句话）。

“感觉不太对”“可能有问题”不报。

## 门禁完整性

门禁是任何能让这次改动失败的检查：测试、断言、阈值、超时、lint、类型检查、CI job、快照。审查时先扫门禁改动，再谈其他。

```sh
node "$SKILL_DIR"/scripts/gate-scan.mjs --base origin/main
```

脚本分三层，不能跳级：

1. **列出**：测试、CI、快照、配置里的每个 hunk，只计数，不算问题；
2. **阅读**：带标签的 hunk（删测试、关测试、快照独改、占位符、环境嗅探、抑制注解、绕过开关、放宽阈值、吞异常），逐个读；
3. **判定**：只问一个问题——**这次放宽是为了掩盖它原本要抓的失败，还是有本 diff 里看得见的测量或决策依据？**

门禁类发现一律**只问人，不自动修**。报告里写清标签、位置、前后值和那句问题；没有依据的放宽按 P1 起。

## 对抗审查

需要更狠地找 bug 时加 `--adversarial`：

- 只接受跑得出证据的发现：失败测试、复现脚本、命令输出；
- 风格、命名、未来风险、个人偏好一律丢弃；
- 每条发现交给 `kelin-verifier` 重跑确认；需要独立模型视角时用 `kelin-delegate --role review`（codex/agy 只读沙箱），返回结果同样走回读剔除；
- 只报告，不修；修不修由人决定。

## 子代理发现的回读剔除

独立审查（`kelin-reviewer` 子代理或外部模型）返回的每条问题，主代理都要**回读对应代码确认成立**才放进结论或交给执行者：读得出位置、对得上触发条件、讲得出后果的才算数；读不出依据的标"待确认"或直接剔除，不把未经核实的问题转手。防的是审查者的幻觉经你之手变成别人的返工单。

**委托审查的提示词必须写死输出契约**：逐条问题以 `文件路径:行号` 开头，跟触发条件、后果、建议；缺位置的条目一律按"待确认"处理，不计入已确认问题数（2026-11-17 fixture eval 实测：codex 侧委托审查没带 file:line，此条即为此而设）。

## 评审指纹

评审必须绑定当时的工作区。审完写回执：

```sh
node "$SKILL_DIR"/scripts/review-check.mjs --write
```

交付前再跑一次：

```sh
node "$SKILL_DIR"/scripts/review-check.mjs
```

`CURRENT` 才算评审有效；`STALE` 说明代码变了，评审作废；`UNVERIFIED` 或 `MISSING` 不能当通过。`kelin-ship` 只接受 `CURRENT`。

## 审查档位（按风险选深度，不一刀切）

| 档 | 适用改动 | 做什么 |
| --- | --- | --- |
| 轻量核验 | 纯样式/文案/排版、辅助脚本（且未碰高风险区） | gate-scan 看改动块，对照复用与文案配对快速核查，给简短结论 |
| 独立深审 | 核心逻辑，或动了并发/数据格式/迁移/删除类不可逆/鉴权支付/对外接口/发布链路 | gate-scan 采集 + 干净上下文五维细审（本 skill 全流程） |

高风险区的定义以目标仓库 AGENTS.md 开发约定为准；没有时按左列类别判断。轻量档不省的只有 gate-scan——门禁改动任何档位都要过。

## 分级

| 级别 | 含义 | 例子 |
| --- | --- | --- |
| P0 | 会丢数据、泄密、把线上搞挂 | 没校验就覆盖用户数据；密钥写进仓库 |
| P1 | 主流程错误，用户能撞上 | 边界条件算错；异常被吞掉 |
| P2 | 局部错误或明显的坑 | 空数组没处理；错误信息误导 |
| P3 | 可读性、命名、重复代码 | 复制粘贴的三段逻辑 |

P0/P1 必须修完才能交付；P2 至少记录；P3 可以留到下次。

## 检查清单

**正确性**
- 主要输入、边界值（空、0、负数、超长、并发）分别会怎样；
- 错误路径有没有被吞掉；
- 时间、时区、编码、小数精度。

**测试**
- 新增行为有没有测试；
- 测试是不是只测了实现细节，没测行为；
- 失败时能不能定位。

**安全与合规**
- 代码/配置/日志里有没有密钥、token、真实客户数据；
- SQL/命令拼接有没有注入风险；
- 权限是不是最小。

**范围**
- 有没有顺手改了不相关的东西；
- 有没有为了绕过一个报错而加的分支/开关/兼容层；
- 删除的代码是不是真的没人用。

## 输出格式

```markdown
## 审查结论
P0: 0 / P1: 1 / P2: 3 / P3: 2 —— 建议：修完 P1 再交付

## P1
1. `src/quote.ts:88` 数量为 0 时除以 0，返回 Infinity，前端显示 ¥∞。
   触发：用户把数量清空再提交。
   建议：数量 <= 0 时直接拒绝并提示。

## 已检查且没问题
- 权限：接口复用了现有鉴权中间件（`src/auth.ts:12`）
```

最后一段“已检查且没问题”很重要：它告诉用户你审了哪些面，而不是只挑刺。

## 反模式

- 把风格偏好当 P0；
- 只报问题不给建议；
- 报了一堆，没排序，用户不知道先修哪个。
