# 交付

交付不是“代码写完了”，是**别人能安全地接过去**。

## 硬规则

1. **一任务一分支。** 分支名说清做什么：`feat/quote-export`、`fix/empty-qty`。
2. **提交信息带 `[ZCode]` 前缀**，第一行说结果，正文说为什么。
3. **进度以远端 main 为准。** 合并前先 rebase/merge 最新 main，别在本地猜。
4. **部署要人点头。** 没听到明确的“部署/上线”，只做到 push + PR。CI 绿不等于可以部署。
5. **真实数据、密钥不进仓库。** 提交前扫一眼暂存区。

## 步骤

### 1. 交付前自审

用 `kelin-review` skill 过一遍，P0/P1 清零。

### 2. 验证

用 `kelin-verify` skill 跑验收清单。把命令和结果写进 PR 正文，不要写“已测试”。

### 3. 提交

```sh
git status --short          # 确认只改了该改的
git diff --stat             # 确认没有意外的文件
git add <明确路径>           # 不用 git add -A
git commit -m "[ZCode] 一句话说结果" -m "为什么这么改，风险是什么"
```

### 4. PR

正文最少四段：

```markdown
## 做了什么
## 怎么验证的
- 命令 + 结果
## 风险与回滚
## 没做的事（以及为什么）
```

### 5. CI

- 红了先看**第一个**失败的 job，找根因，不要重跑到绿；
- 网络抖动导致的失败，说明后重跑一次；
- 不要为了过 CI 改测试或加 `--force`。

### 6. 合并与收尾

- 合并后确认远端 main 上有你的提交；
- 删除本地分支，清理临时文件；
- 如果这次交付改变了“怎么工作”，交给 `kelin-reflect` 沉淀。

## 部署（只有明确授权才执行）

1. 确认部署清单：改了什么、影响谁、回滚命令是什么；
2. 先在能回滚的前提下执行；
3. 部署后立刻验证：健康检查、关键页面、关键接口；
4. 出问题先回滚，再分析。

## 反模式

- 在 main 上直接改；
- PR 正文只有“update”；
- CI 红了反复重跑；
- “顺便”把别的改动塞进同一个 PR。

## 提交前检查

```sh
node skills/kelin-ship/scripts/preflight.mjs
```

在暂存之后执行。它检查：是不是直接在 main/master、有没有暂存表格类真实数据、暂存内容里有没有密钥特征。有问题退出 1，并列出文件；通过退出 0。
