# 精炼

精炼不是“写得更短”，是**让每一行都必须存在**。

## 必要性阶梯

动笔或审查时，按顺序问：

1. 这东西需要存在吗？没人要的功能、选项、灵活性，删；
2. 仓库里已经有了吗？有就复用，按周围代码的写法用；
3. 标准库或平台自带吗？用现成的，别自己写；
4. 已装的依赖能做吗？能做就用，不要为几行代码加新依赖；
5. 能写成一眼看懂的一行吗？能就一行；
6. 以上都不行，才写最小实现。

## 删什么

- 死代码、没人用的导出、没人设的配置；
- 只有一个实现的接口/工厂/包装层；
- 为“以后可能用”预留的参数和分支；
- 内部信任边界内多余的防御性 `try/catch` 与兜底分支；
- 复制粘贴后略改的两段逻辑，合成一处；
- 只为凑短函数拆出的小 helper；
- 复述代码或替怪代码辩解的注释。

## 不删什么

信任边界校验（用户输入/外部接口/文件）、防丢数据错误处理、安全逻辑、无障碍与硬件校准、用户明确要求的功能。精简只针对“多余”，不针对“必要”。

## 代码即注释

代码本身就是注释；自家代码的怪行为是**重构目标**（改名、拆函数、建类型），不是长注释的理由。改完做一轮只读注释审查：

- **仅五类可留**：法律头、无法改变的外部依赖/平台/协议约束（须可验证）、`prettier-ignore` 等纯风格指令、公共 API 契约、issue/RFC 链接；
- **临时债务**：允许单行 `// shortcut: <限制>; <升级条件>`，超限即升级；
- **必清或重构**：复述代码、注释尸体、自家代码辩解、过期 TODO；验证脚本不写分步旁白注释，意图写进断言消息；
- **约束注释**（`IMPORTANT`/`do not remove`）：查 git 历史与现行行为，仍成立就编码进类型/测试/lint 后删，过期直接删；
- **抑制注解**（`eslint-disable`/`@ts-ignore`）：diff 审查逐条核定，严禁遮盖正确性或安全错（类型负测 `@ts-expect-error` 除外）；存疑标 `REVIEW`。

## 对 diff 做一次 over-engineering 审查

```sh
git diff --stat
git diff
```

对每一处新增问：

- 这行能不能删掉而行为不变？
- 这个抽象现在只有一个使用者吗？
- 这个参数有人传非默认值吗？
- 这段和仓库里哪个已有实现重复？
- 加了新依赖吗？它值这几行吗？

## 改完必须重跑验证

精简会改行为，尤其是合并分支和删除“看起来没用”的代码。改完重跑 `verify`，不要凭眼力判断。

## 输出

```markdown
## 精炼结果
- 删除：<文件:行>，原因
- 合并：<两处路径> → <一处>
- 保留：<看起来可疑但必须留的>，原因
- 行数：-N
## 验证
- 命令 + 结果
```

## 反模式

- 为了短而牺牲可读性；
- 把校验、错误处理当“冗余”删掉；
- 一次重构太多，验证失败后不知道是哪处改坏的；
- 删了代码不重跑测试。
