# 精炼

精炼不是“写得更短”，是**让每一行都必须存在**。

## 必要性阶梯

动笔或审查时，按顺序问：

1. 这东西需要存在吗？没人要的功能、选项、灵活性，删；
2. 仓库里已经有了吗？有就复用，按周围代码的写法用；
3. 标准库或平台自带吗？用现成的，别自己写；
4. 已装的依赖能做吗？能做就用，不要为几行代码加新依赖；
5. 能写成一眼看懂的一行吗？能就一行；
6. 以上都不行，才写最小实现。

## 删什么

- 死代码、没人用的导出、没人设的配置；
- 只有一个实现的接口/工厂/包装层；
- 为了“以后可能用”预留的参数和分支；
- 复制粘贴后略微改动的两段逻辑，合成一处；
- 只为了让函数变短而拆出来的小helper；
- 复述代码的注释（`// 循环数组`、`// 返回结果`）。

## 不删什么

- 信任边界上的校验（用户输入、外部接口、文件内容）；
- 防止丢数据的错误处理；
- 安全相关逻辑；
- 无障碍和真实硬件需要的校准；
- 用户明确要求的东西。

精简只针对“多余”，不针对“必要”。

## 注释规则

只写代码表达不了的**为什么**，一行。允许这一种带限制的注释：

```
// shortcut: 只支持单进程；多实例部署前必须换成分布式锁
```

它不是借口，是记录债务；超过限制就该升级。

## 对 diff 做一次 over-engineering 审查

```sh
git diff --stat
git diff
```

对每一处新增问：

- 这行能不能删掉而行为不变？
- 这个抽象现在只有一个使用者吗？
- 这个参数有人传非默认值吗？
- 这段和仓库里哪个已有实现重复？
- 加了新依赖吗？它值这几行吗？

## 改完必须重跑验证

精简会改行为，尤其是合并分支和删除“看起来没用”的代码。改完重跑 `verify`，不要凭眼力判断。

## 输出

```markdown
## 精炼结果
- 删除：<文件:行>，原因
- 合并：<两处路径> → <一处>
- 保留：<看起来可疑但必须留的>，原因
- 行数：-N
## 验证
- 命令 + 结果
```

## 反模式

- 为了短而牺牲可读性；
- 把校验、错误处理当“冗余”删掉；
- 一次重构太多，验证失败后不知道是哪处改坏的；
- 删了代码不重跑测试。
