# 规划

> 命令里的 `$SKILL_DIR` 指本 Skill 所在目录的绝对路径，执行前先替换成实际路径。

目标不是写一份漂亮的文档，是**在写代码之前把错误的方向挡掉**。

## 什么时候必须用

- 改动跨 2 个以上文件，或涉及数据/权限/对外接口；
- 需求里有“优化”“重构”“支持一下”这类模糊词，或你不确定验收标准；
- 上次类似任务的结论是“做完发现方向错了”。

小修小补（改文案、调样式、单行 bug）不用走这套。做软件/功能/系统（有用户、权限、上传导出）时先读 `kelin-product` 定边界与性能预算。

## 计划的三档

| 档 | 用在哪 | 写什么 |
| --- | --- | --- |
| 轻量 | 单文件、不到 30 分钟 | 三行：目标 / 验收 / 下一步 |
| 标准 | 跨文件 | 下面这套完整模板 |
| 完整 | 跨模块、动数据、对外接口 | 标准 + 设计草图 + 影响面 + 决策记录 |

先用轻量，不够再加。检查结构完整与依赖无环：

```sh
node "$SKILL_DIR"/scripts/check-plan.mjs plan.md
node "$SKILL_DIR"/scripts/check-plan.mjs plan.md --level light
```

## 步骤

### 1. 复述目标，写死验收

用三句话写：谁在什么场景遇什么问题、做完能做什么、**怎么证明做到了**（命令/页面/数字）。写不出可执行验收说明还没想清，停下来问。

### 2. 摸清现状（只读）

- 相关代码在哪、谁在调用、有没有现成实现；
- 数据从哪来、写到哪去、量级多少；
- 现有测试覆盖了什么、缺什么、和既有约定是否冲突。
- 对接插件钩子、IM 协议、网络、开放接口前，先在真环境跑 10 行级小探针确认真实行为，不靠猜写大代码。

不要在这一步改任何东西。

### 3. 给方案，带推荐（先实验再推荐）

列 2-3 个可行方案（怎么做、代价、风险、何时不合适），最后给**明确推荐**。若关键分叉低成本、可逆且能实测区分，先在隔离目录做一次抛弃式小实验拿实测数据再推荐，不空口问人。

### 4. 拆成可验证的单元

每个单元一次可做完、系统仍可用、写明**文件边界 + 依赖 + 独立真实验证方式**（不止单测；含真实接口/命令/性能失败线）。先切用户能最快摸到的最小闭环独立上线，再并行补外围或运维，不把能先用的捆死；预计单插件/脚本超 500-600 行难收住就换直白方案。用 `依赖：单元 X` 标出顺序与可并行项。

### 5. 写下来

输出到 `design.md` 和 `plan.md`：

```markdown
# 目标
# 验收标准
- [ ] 命令/页面/数字
# 现状
# 方案与取舍
# 推荐
# 本期不做
- <明确划出去的相邻功能与顺手蔓延项>
# 任务拆解
- [ ] 单元 1：做什么 / 依赖：无 / 验证：<真实命令与结果>
# 风险与回滚
```

**"本期不做"必须写**：防范围蔓延的事前闸门；每条任务拆解必须带验证方式。对照：

| 维度 | 写了等于没写 | 清晰的写法 |
| --- | --- | --- |
| 外部变化 | 重构导出状态机并接取消令牌 | 点取消后立即停编码并删半成品，按钮恢复可再导出 |
| 范围复用 | 修改导出模块与弹窗视图 | 复用弹窗组件；改调度器传中止信号；**本期不做**断点续传 |
| 验证 | 运行测试确保通过 | 局部快测 + 真实取消端到端命令与结果 |

### 6. 停下来

除非用户已明确授权“直接做”，否则给用户看并等确认。

## 设计草图（完整档必做）

六块内容：1. **类型与签名**（目标语言、在边界解析外部数据）；2. **模块边界**（调用方需要知道多少、每份状态唯一写入者）；3. **数据流**；4. **失败模式**（超时/重复/部分成功/并发）；5. **不做的事**；6. **技术栈与理由**（按用户环境选）。

先用 [references/design-red-flags.md](references/design-red-flags.md) 过 8 条 AI 设计红旗（薄模块、信息泄漏、按执行顺序拆、直通、所有权分裂、两套做法、内部可导、手工同步清单），再独立写 2 个不同候选（模板：[templates/candidates.md](templates/candidates.md)），用 `kelin-reviewer` 交叉评分后推荐，停在草图等确认。

## 计划评审门（feature / legacy）

跨模块或动数据/权限的计划，写完后过两道镜头再开工：1. **产品镜头**（值不值得做、最小范围）；2. **工程镜头**（类型边界、失败模式、测试与回滚）。

- 最多 2 个子代理；`budget.mjs` 的 `maxAgents < 2` 时由主代理自己做；
- 只把需要人拍板的项交给用户；每道镜头必须写非空 `summary`/`verdict`，并绑定 `plan.md` 的 `planHash`；
- 校验命令：

```sh
node "$SKILL_DIR"/scripts/plan-gate.mjs plan-gate.json --plan plan.md --require-resolved
```

有 `pending` 决策、空镜头或 `planHash` 过期就退出 1，不要进 build。修 bug、单文件、文案改动跳过这道门。

## 反模式

- 把计划写成愿望清单或空镜头走过场；
- 拆出的单元相互循环依赖或没写验证方式；
- 改了 `plan.md` 却复用旧 `plan-gate.json`。

## 下游衔接

| 下一步 | 去哪 |
| --- | --- |
| 方案确认，开始实现 | `kelin-mode` build 阶段（`kelin-tdd`） |
| 需求模糊 / 专家视角缺口 | `kelin-grill` 或 `kelin-goal` 先收敛 |
| 原因不明的故障 | `kelin-correctness` 定位根因 |
