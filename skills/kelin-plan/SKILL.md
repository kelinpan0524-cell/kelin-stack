# 规划

目标不是写一份漂亮的文档，是**在写代码之前把错误的方向挡掉**。

## 什么时候必须用

- 改动跨 2 个以上文件，或涉及数据/权限/对外接口；
- 需求里有“优化”“重构”“支持一下”这类模糊词；
- 你不确定验收标准是什么；
- 上次类似任务的结论是“做完发现方向错了”。

小修小补（改文案、调样式、单行 bug）不用走这套。

## 计划的三档

| 档 | 用在哪 | 写什么 |
| --- | --- | --- |
| 轻量 | 单文件、不到 30 分钟 | 三行：目标 / 验收 / 下一步 |
| 标准 | 跨文件 | 下面这套完整模板 |
| 完整 | 跨模块、动数据、对外接口 | 标准 + 影响面 + 决策记录 |

先用轻量，不够再加。不要给单文件任务写十页计划——那是另一种浪费。

```sh
node skills/kelin-plan/scripts/check-plan.mjs plan.md --level light
```

## 步骤

### 1. 复述目标，写死验收

用三句话写：

- 谁在什么场景下，遇到什么问题；
- 做完之后，他能做什么之前做不到的事；
- **怎么证明做到了**：一条能跑的命令、一个能看的页面、一份能对的数字。

验收标准写不出可执行形式，说明还没想清楚，停下来问。

### 2. 摸清现状（只读）

- 相关代码在哪、谁在调用、有没有现成实现；
- 数据从哪来、写到哪去、量级多少；
- 现有测试覆盖了什么、缺什么；
- 有没有和需求冲突的既有约定（AGENTS.md、部署流程、命名习惯）。

不要在这一步改任何东西。

### 3. 给方案，带推荐

列 2-3 个可行方案，每个写：怎么做、代价、风险、什么时候不合适。

**最后必须给一个明确推荐**，并说明为什么。不要把选择权原样丢回给用户。

### 4. 拆成可验证的单元

每个单元满足：

- 一次能做完（半天到两天）；
- 有独立的验证方式；
- 做完之后系统仍然是可用的（不是“拆到一半不能用”）。

按依赖排序。标出哪些单元可以并行。

### 5. 写下来

输出到 `design.md`（设计）和 `plan.md`（任务），模板：

```markdown
# 目标
# 验收标准
- [ ] 命令/页面/数字
# 现状
# 方案与取舍
# 推荐
# 任务拆解
- [ ] 单元 1：做什么 / 怎么验证 / 依赖
# 风险与回滚
```

### 6. 停下来

除非用户已经明确授权“直接做”，否则把方案给用户看，等确认。规划的价值在于**在便宜的时候发现方向错了**。

## 反模式

- 把计划写成愿望清单，没有验收；
- 只给一个方案，没有取舍；
- 拆出来的单元互相依赖成一串，没法独立验证；
- 规划完直接开写，没给用户看。

## 配套脚本

```sh
node skills/kelin-plan/scripts/check-plan.mjs plan.md
```

退出 0 表示结构完整：有目标、验收标准、方案/推荐、任务拆解、风险，且任务里写了怎么验证。退出 1 会列出缺哪节。放进 CI，计划就不会退化成愿望清单。
