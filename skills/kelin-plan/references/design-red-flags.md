# 设计红旗清单与多阶段实验准则

起草设计草图或评审候选方案时，先用这 8 条红旗逐个过筛；命中任一条且无充分理由，就重写形状，不靠注释或补丁硬兜。

## 8 条 AI 视角设计红旗

| 红旗 | 典型坏味道 | 最小改法 |
| --- | --- | --- |
| 1. 薄模块 | 接口一大堆，里面只藏了几行逻辑 | 合并进有能力的模块，让接口更窄 |
| 2. 信息泄漏 | 多个模块同时依赖同一内部格式或协议细节 | 把外部格式在边界解析成领域类型，内部不外露 |
| 3. 按执行顺序拆模块 | 硬拆成 load/validate/save 三段，同一个不变量在每段重复校验 | 按**领域知识和状态归属**聚成模块 |
| 4. 直通方法 | A 方法把原参数透传给 B，自己不加任何策略或适配 | 删掉中转层，直接调拥有者 |
| 5. 所有权分裂 | 两个以上模块或文件都能改同一份状态（改一处漏另一处） | 指定唯一写入者，其余方只读或发请求 |
| 6. 一件事留两套做法 | 新旧写法或两条路径并存（AI 会复制先看到的那条） | 统一成一条入口，**同批把旧路径和旧调用方删净** |
| 7. 内部细节可被外部导入 | 外部可以直接 import 内部 helper（AI 会走最短可编译路径） | 收窄导出边界，跨边界调用从公共入口走 |
| 8. 手工同步清单 | 两个文件/枚举各自列同一份清单，加一项要同时改两处 | 保留唯一真相源并派生其余，或用校验脚本在构建期卡死 |

## 调用方视角两问

1. 调用方需要知道多少内部概念才能把事办成？（越少越好）
2. 错的输入能不能在边界一次拦截，让内部逻辑不用到处判空？（`unknown`/外部数据在边界解析）

## 多阶段与先验实验规则

- **低成本可逆分叉先做抛弃式小实验**：能写 20 行临时脚本测出结果（性能、兼容性、接口返回），先跑出观察结论再推荐，不空口写计划。
- **多 PR / 多阶段计划三盒验收**：每单元必须写清「改动文件边界」「依赖谁」「唯一职责」「真实操作验收（不止单元测试）」「涉及性能时的度量与失败线」。
- **计划锁哈希**：`plan.md` 改过一行，`plan-gate.json` 里的 `planHash` 必须同步重签，不允许旧评审背书新计划。
