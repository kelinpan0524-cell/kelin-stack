# 产品设计底线

这套底线解决的是“做出来才发现不对”：给错的人、在错的设备上、权限没设计、数据入口没防错、性能预算没定。**这些都要在 plan 期问清楚，不是上线前补。**

## 第一件事：问清用户和环境

不问清楚就别选技术栈。

| 要问 | 为什么 |
| --- | --- |
| 谁用：岗位、人数、是否外部客户 | 决定权限模型和界面密度 |
| 设备：公司电脑、老笔记本、手机、平板 | 决定性能预算和交互方式 |
| 网络：内网、弱网、离线 | 决定缓存、同步、包大小 |
| 使用频率：每天几十次还是每月一次 | 决定快捷操作和引导 |
| 数据量：百行、万行、百万行 | 决定分页、导入方式、数据库 |
| 合规：客户数据、手机号、金额 | 决定脱敏、审计、权限 |

答案写进 PRD 的“目标用户与环境”一节。**没有答案就标“待确认”，不要默认所有人。**

## 需求澄清：最多留 3 个问号

把已确定的写下来，不确定的标 `[待确认]`；不要用“大概”“应该”“先做起来看”糊过去。

只有同时满足三条才值得停下来问：选错会明显改变范围或体验；有多个合理解释且结果不同；没有行业默认值可用。

其余用默认值，写进 PRD 的“假设”一节（数据留多久、并发多少、错误怎么提示）。**默认值要让人看见，才有机会被推翻。**

- 一份 PRD 最多 3 个会卡住开工的 `[待确认]`，每个写清“谁回答、卡住哪条需求”；超过 3 个说明还没到能开工的程度；
- 其余疑问写成带负责人的开放问题，放 PRD 末尾，不阻塞开工；
- **不发明需求**：没说的功能不补，没给的数字不编；每条都能追到原话、数据或明确假设。

## 用户旅程写到能演一遍

不要写“用户可以管理订单”，写具体的人、按顺序发生的事：

1. **谁**：给名字和身份——“报价员小李”，不是“用户”；
2. **从哪进来**：已登录？从消息点进来？手上有什么数据？
3. **3-5 个动作**：每步看到什么、点什么、系统回什么；
4. **价值在哪一刻落地**：哪个数字或状态让他知道事情成了；
5. **一条失败路径**：网络断、权限不够、数据不对时怎么走。

写不出具体场景，说明还没见过真实用法，先去问或看现场。一段旅程对应一组需求，每条需求能指回某段旅程。

## 先定胃口，再谈方案

设计前先问：**这件事值多少时间？** 不是估工期，是先定花多少时间值得。时间定死，范围可砍。

每个方案写清：解决谁的什么问题、胃口（几天/几周）、做法（粗糙但完整）、兔子洞（第三方对接、历史数据清洗、权限边界、离线同步，能绕就绕）、这次明确不做什么。

到点没做完，砍范围或停，不自动延期。方案保持低精度，细节留到设计阶段。

## 技术栈在 plan 期定

按环境选，不按流行选：老设备、弱网优先轻量、服务端渲染或少 JS；内部工具优先成熟可维护，不追新框架；数据量大先定分页、索引、导入策略再选库；只有一两个人维护就少依赖、少构建步骤。

技术栈选择写清：选了什么、为什么、放弃了什么。不要“先用着再说”。

## 数据入口：上传必须防错

Excel / CSV 上传按这个顺序：

1. **预检**：文件类型、大小、编码、表头是否匹配、行数上限；
2. **解析预览**：先解析到临时区，展示前 N 行和总行数；
3. **清洗**：去空行、去重、日期/金额格式统一、必填校验；
4. **错误报告**：按行号 + 列名 + 原因列出，能下载错误清单；
5. **人工确认**：用户看过预览和错误数，点确认才写库；
6. **可回滚**：记录批次号，支持撤销整批导入。

任何一步失败都不写正式表。**不允许“上传即入库”。**

## 数据出口与大数据

- 导出格式、列顺序、表头、日期和金额格式与页面一致；导出动作记审计日志；
- 大数据量分页或流式导出，不一次性塞内存；
- 列表默认每页 20-50 行；超过 1000 行必须服务端分页或虚拟滚动；
- 搜索、排序、筛选在服务端做；导出和列表用同一套筛选条件，避免“看到的和导出的不一样”。

## 权限与审批：第一天就设计

**权限矩阵**写进 PRD：角色 × 资源 × 动作（查看/新增/编辑/删除/导出/审批）。

- 最小权限，默认拒绝；申请人不能审批自己的单；
- 高风险动作（删除、导出客户数据、改金额、改权限）要双人复核或二次确认；
- 审批流每个卡点写清：谁审、看什么、超时怎么办、驳回后回到哪；
- 所有审批和权限变更留审计日志；权限变更本身也要审批，不能一个人给自己加权限。

目标是：**一个人的错误，不能变成所有人的损失。**

## 批量修改：数据多时必须能改

1. 多选或按筛选结果全选，范围写清楚（本页 / 全部筛选结果）；
2. 只允许白名单字段批量改；输入新值，逐行校验；
3. **预览 diff**：将改多少行、冲突多少行、失败多少行；
4. 部分失败给行号 + 原因；成功的先不提交，或整批回滚；
5. 提交后按批次号可撤销；
6. 全程审计：谁、改了哪些行、旧值和新值。

超过 1000 行走异步任务：有进度、可取消、完成后通知。并发编辑用乐观锁，冲突让人选保留哪边。

## 导航与侧边栏：入口怎么放

侧边栏最容易被开发顺序带歪——谁的模块先做完，谁的入口就排最前面。定三条：

**按用途分组，不按开发顺序。** 常用入口一组、项目/模块类一组、内容/资料类一组。组间拉开间距加小标题；分割线只用来划分大块区域，不要每个入口都画线。

**当前位置要一眼看见。** 选中项垫颜色醒目的底块，未选中项对比度降一档但仍可读（不低于 4.5:1）；只靠加粗或轻微变色不算标注。

**固定两头，中间可滚。** 设置、帮助、账户放底部固定；升级/付费入口可往下放，但不许折叠隐藏。入口多到排不下时，顶部和底部固定、中间滚动。

入口顺序**定了就不随意改**（用户靠位置记忆找入口）；同一个入口只允许有一个家，不在页面里再放一遍。自查：入口超过 7 个就该分组；收起状态下列不全的，说明该归档或合并。

## 界面别一眼是 AI 做的

七步是减法，顺序不能乱：先砍最扎眼的，再调结构，最后修文案。

1. **去渐变和发光**：背景、卡片、按钮全换纯色，去掉光晕、毛玻璃、发光描边。AI 味最重的来源，先砍这个。
2. **颜色收到一个主色**：底色用纸感的浅色（不是纯白也不是死灰），强调色只留一个，只用在最该被看见的地方（进度、当前项）。
3. **emoji 换线性图标**：装饰性 emoji 全部换掉；图标统一线性、同一粗细、同一视觉重量。
4. **少用卡片**：不是每块内容都要装进圆角盒子；用留白和细分隔线分区，页面立刻透气。
5. **定主次**：一屏只有一个视觉重心，其余功能收成一排小图标；对照用户打开这一屏最想干的那件事。
6. **换字体**：标题可用衬线，数字用细衬线，正文保持无衬线；全站字重不超过三档。
7. **改文案**：把“欢迎回来，XX”换成具体信息（今天的日期、上次读到哪、还差多少）；按钮写清动作，“从上次停下的地方继续”好过“立即阅读”。

自查：截图后眯眼看——第一眼像模板，回做第 1、2、4 步；第一眼不知道该干什么，回做第 5、7 步。

## 下拉菜单和选择器不是一回事

- **选择器（select）**：填表用，选中的值留在框里，跟表单一起提交；外形像输入框，显示当前值。
- **下拉菜单（dropdown / 更多）**：命令集合，本质是一排藏起来的按钮；点一项立刻执行（导出、删除、跳转设置），触发按钮上不会留下“你选了什么”。

规则：后台表格**顶部筛选用带框的 select，右侧操作列用纯文字或图标触发的 dropdown**，不要做成同一个样式——用户点之前分不清是筛选还是删数据。选项 **≤2 个**用单选或开关，**少于 5 个**直接平铺，再多才收进 select。选项多（年份、城市）**加搜索**，面板高度控制在一屏扫得完（参考 256px）。用户能直接说出来的值（出生年份、金额）**让他输入**，别让人滑一百行。弹层方向看下方剩余空间：够就往下、不够就往上；手机端选项多时从底部划出整块面板，**同一个 App 里不要上下左右随意弹**。

## 性能预算

写进 PRD，按目标设备定。默认参考：

| 指标 | 默认目标 |
| --- | --- |
| 首屏可交互 | 弱设备 < 3 秒，普通设备 < 2 秒 |
| 常驻内存 | 桌面工具 < 200MB |
| 首屏 JS | 能少则少，内部工具不为一屏动画加几百 KB |
| 列表 | 默认分页，单页不超过 50 行 |
| 缓存 | 静态资源长缓存，业务数据明确失效策略 |

不做花里胡哨的动效和重组件；先保证打开快、不卡、不崩。

## AI 解析：人只做决策

- AI 输出**先预览**，高亮不确定项和置信度；每条结果可编辑、可撤销、可追溯来源；
- **人工确认后才落库**，不允许 AI 直接改正式数据；
- 批量结果给汇总：共多少条、多少条需人工处理；出错时给原文件和行号，能回到原文。

## 验收标准：外行也能判对错

每条验收 = 一个能观察的结果 + 判断标准。技术细节不算验收。

- **可测**：带数字、单位或能跑的命令——“报价 3 分钟内完成”“10 万行翻页 < 1 秒”“`npm test` 退出 0”；
- **技术无关**：写用户看到什么，不写“接口 < 200ms”“用了 Redis”；实现指标放性能预算或设计文档；
- **关键路径用 Given/When/Then**：当 <前置状态>，做 <动作>，则 <结果>；失败路径至少一条：当 <异常>，则 <提示与恢复>；
- **优先级**：P1 单独做完就能演示、能验证；P2/P3 才允许依赖 P1。每条故事独立可测。

反例：验收写“界面美观”“功能正常”“性能良好”——没法判，等于没写。

## PRD 怎么写

**先定高度，再动笔。** 一份 PRD 只停在一个高度：

| 高度 | 写到什么 | 不写什么 |
| --- | --- | --- |
| 项目/项目群 | 为什么做、给谁、成功指标、大方向和顺序 | 具体功能行为、页面、接口 |
| 一个系统/功能 | 问题、用户旅程、能力清单（每条一个可验收结果）、边界 | 表结构、接口签名、页面细节 |
| 一个迭代切片 | 可测的需求、异常和失败状态、这次改什么/不改什么 | 上层写过的目标和指标，引用编号即可 |

混高度的 PRD 最难读：上面没结论，下面全是细节。

**必含**：目标用户与环境、用户旅程、能力与优先级、术语表（有领域名词时）、导航结构、权限矩阵、数据入口与出口、异常与防错、性能预算、验收标准、不做的事、技术栈与理由、待确认与开放问题（每个带负责人）。

**篇幅**：小项目一页；一个系统 2-3 页；写不下就拆到下一层，不要靠加长装完整。**术语表**：客户/用户/订单/报价单这类词，第一次出现就定死含义和关系，全篇只用一个词。

但 **PRD 不是一次做对**：先写确定的部分，标 `[待确认]`；迭代中发现的新事实回写 PRD 并记决策日志；不追求一次写全，追求每次改动都有记录、下一个人能看懂；旧 PRD 是历史，不是现状，收尾用 `kelin-neat` 对齐。

校验：

```sh
node skills/kelin-product/scripts/prd-check.mjs PRD.md
```

## 什么时候自动写 plan

出现任一信号就写：跨 2 个以上文件；涉及数据/权限/上传/导出；需求里有“做个软件/功能/系统”；用户说不清验收或上次返工过；要给特定人群用。

单文件、文案、明确的小修不硬写。判断标准在 `kelin-plan`。

## 反模式

- 先选框架再问用户用什么设备；
- 需求没说清就开工，边做边猜，代码写完才发现做错了人；
- 一份 PRD 留七八个“待确认”，没有一个人负责；
- 验收写“功能正常 / 界面美观”，上线时靠感觉判；
- 目标、页面、表结构混在一份 PRD 里，谁也读不完；
- 时间到了没做完就自动延期，不砍范围；
- 上传直接写库，出错再手工修；列表一次拉全量；
- 权限最后加，发现到处是洞；审批流只有一个人能批；
- AI 结果直接提交，没有预览；
- 侧边栏按开发顺序排入口，选中态只靠加粗；
- 升级/付费入口怕丑就藏起来，或塞进“更多”；
- PRD 写完就不改，代码和文档两张皮。
