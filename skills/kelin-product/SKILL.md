# 产品设计底线

这套底线解决的是“做出来才发现不对”：给错的人、在错的设备上、权限没设计、数据入口没防错、性能预算没定。**这些都要在 plan 期问清楚，不是上线前补。**

## 第一件事：问清用户和环境

不问清楚就别选技术栈。

| 要问 | 为什么 |
| --- | --- |
| 谁用：岗位、人数、是否外部客户 | 决定权限模型和界面密度 |
| 设备：公司电脑、老笔记本、手机、平板 | 决定性能预算和交互方式 |
| 网络：内网、弱网、离线 | 决定缓存、同步、包大小 |
| 使用频率：每天几十次还是每月一次 | 决定快捷操作和引导 |
| 数据量：百行、万行、百万行 | 决定分页、导入方式、数据库 |
| 合规：客户数据、手机号、金额 | 决定脱敏、审计、权限 |

答案写进 PRD 的“目标用户与环境”一节。**没有答案就标“待确认”，不要默认所有人。**

## 技术栈在 plan 期定

按环境选，不按流行选：

- 老设备、弱网：优先轻量、服务端渲染或少 JS；
- 内部工具：优先成熟、可维护，不追新框架；
- 数据量大：先定分页/索引/导入策略，再选库；
- 只有一两个人维护：优先少依赖、少构建步骤。

技术栈选择写清：选了什么、为什么、放弃了什么。不要“先用着再说”。

## 数据入口：上传必须防错

Excel / CSV 上传按这个顺序：

1. **预检**：文件类型、大小、编码、表头是否匹配、行数上限；
2. **解析预览**：先解析到临时区，展示前 N 行和总行数；
3. **清洗**：去空行、去重、日期/金额格式统一、必填校验；
4. **错误报告**：按行号 + 列名 + 原因列出，能下载错误清单；
5. **人工确认**：用户看过预览和错误数，点确认才写库；
6. **可回滚**：记录批次号，支持撤销整批导入。

任何一步失败都不写正式表。**不允许“上传即入库”。**

## 数据出口：导出要保真

- 导出格式、列顺序、表头、日期和金额格式与页面一致；
- 大数据量分页导出或流式导出，不一次性塞内存；
- 导出动作记审计日志（谁、什么时候、导出了什么范围）。

## 大数据：分页是默认

- 列表默认每页 20-50 行；
- 超过 1000 行必须服务端分页或虚拟滚动；
- 搜索、排序、筛选在服务端做，不把全量拉到前端；
- 导出和列表用同一套筛选条件，避免“看到的和导出的不一样”。

## 权限与审批：第一天就设计

**权限矩阵**写进 PRD：角色 × 资源 × 动作（查看/新增/编辑/删除/导出/审批）。

默认规则：

- 最小权限，默认拒绝；
- 申请人不能审批自己的单；
- 高风险动作（删除、导出客户数据、改金额、改权限）要双人复核或二次确认；
- 审批流每个卡点写清：谁审、看什么、超时怎么办、驳回后回到哪；
- 所有审批和权限变更留审计日志，能追溯；
- 权限变更本身也要审批，不能一个人给自己加权限。

目标是：**一个人的错误，不能变成所有人的损失。**

## 性能预算

写进 PRD，按目标设备定。默认参考：

| 指标 | 默认目标 |
| --- | --- |
| 首屏可交互 | 弱设备 < 3 秒，普通设备 < 2 秒 |
| 常驻内存 | 桌面工具 < 200MB |
| 首屏 JS | 能少则少，内部工具不为一屏动画加几百 KB |
| 列表 | 默认分页，单页不超过 50 行 |
| 缓存 | 静态资源长缓存，业务数据明确失效策略 |

不做花里胡哨的动效和重组件；先保证打开快、不卡、不崩。

## AI 解析：人只做决策

AI 负责把非结构化变成结构化，人负责确认和决策：

- AI 输出**先预览**，高亮不确定项和置信度；
- 每条结果可编辑、可撤销、可追溯来源；
- **人工确认后才落库**，不允许 AI 直接改正式数据；
- 批量结果给汇总：共多少条、多少条需人工处理；
- 出错时给原文件和行号，能回到原文。

## PRD 怎么写

必含：目标用户与环境、核心流程、权限矩阵、数据入口与出口、异常与防错、性能预算、验收标准、不做的事、技术栈与理由。

但 **PRD 不是一次做对**：

- 先写当前确定的部分，标“待确认”；
- 迭代中发现的新事实，回写 PRD 并记决策日志；
- 不追求一次写全，追求每次改动都有记录、下一个人能看懂；
- 旧 PRD 是历史，不是现状；收尾用 `kelin-neat` 对齐。

校验：

```sh
node skills/kelin-product/scripts/prd-check.mjs PRD.md
```

## 什么时候自动写 plan

不用等用户说“plan”。出现任一信号就该写：

- 跨 2 个以上文件，或涉及数据/权限/上传/导出；
- 需求里有“做个软件/功能/系统”“支持上传”“加权限”；
- 用户说不清验收，或上次类似任务返工过；
- 要给特定人群用，需要先问环境和约束。

反过来，单文件、文案、明确的小修，不要硬写 plan。判断标准在 `kelin-plan` 里。

## 反模式

- 先选框架再问用户用什么设备；
- 上传直接写库，出错再手工修；
- 列表一次拉全量；
- 权限最后加，发现到处是洞；
- 审批流只有一个人能批；
- AI 结果直接提交，没有预览；
- PRD 写完就不改，代码和文档两张皮。
